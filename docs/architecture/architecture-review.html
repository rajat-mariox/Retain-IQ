02Table 2 — "One service per data type"

Proposes 10 services: Organization / Identity / Employee / Attendance / Leave / Payroll / Activity / Productivity / AI / Notification.

Verdict ✗ DON'T DO THIS YET

"One service per data type" is a textbook rule that backfires on real early-stage SaaS. At your scale (testing phase, a handful of live orgs) it adds far more complexity than it removes.

◆ Today (correct)

  • Employee → identity
  • Attendance → identity
  • Leave → identity
  • Payroll → identity
  • Join in one DB transaction
  • 0 network hops between them

◆ Proposed (expensive)

  • Employee Service + DB
  • Attendance Service + DB
  • Leave Service + DB
  • Payroll Service + DB
  • Distributed txn / saga
  • 4–5 network hops / request

Why it's the wrong move — three concrete reasons:

  • These modules are tightly coupled. Payroll reads attendance + leave + rates. Leave affects attendance. Split them into services and every payroll run has to call 3–4 services over the network — what is a single SQL join today. You'd add latency and failure points and gain nothing.
  • The pain of distributed transactions. "Create an employee + create an attendance record" is one atomic DB transaction today. Across services it becomes a saga — eventual consistency, compensating actions, partial-failure handling. That complexity is only worth taking on when a module genuinely needs to scale or be owned separately.
  • The industry doesn't work this way. Stripe, Linear, Notion all started as modular monoliths, then extracted modules one at a time when a real pain forced it. You already extracted billing (correctly — it has a distinct lifecycle). Extracting the rest now is a solution ahead of any problem.

The right mental model: read the table's "Owner" column as module ownership, not service ownership. You already have an Attendance module that owns attendance, a Leave module that owns leave — they simply live inside one service. Ownership is already clean; the deployment boundary doesn't need to be separate.

Large Ent. Optional dedicated Postgres cluster Far off. Only when a real, paying, demanding customer needs it ⚠ LATER

Verdict ✓ CONCEPT IS SOUND

This tiered-isolation pattern is standard for large B2B SaaS (the Salesforce / Workday tier). You're at Tier 1, and that's exactly what you need right now. Tier 2/3 is a feature to build when demand appears — building it now means schema-routing complexity for zero enterprise customers.

Your current design allows for it without a rewrite: because everything is orgId-scoped and DB connections are config-driven, routing a future enterprise org to its own schema/DB is an additive change, not a re-architecture.

Bottom line

  • Table 1 (isolation): Keep it as a roadmap. Tier 1 is done. Build Tier 2/3 only when an enterprise customer actually asks — not before.
  • Table 2 (10 services): Don't implement it. Treat "Owner" as module ownership. Your feature-clustered services + database-per-service already give clean ownership without the distributed-systems tax.
  • When should you extract? A module should become its own service only when one of these is true: (a) it needs to scale independently, (b) a separate team owns it, (c) it has a distinct lifecycle / deploy cadence, or (d) a separate compliance boundary. Billing met that bar — that's why it was extracted. Attendance / Leave / Payroll don't yet.

In one line: your architecture is already "right" for this stage. This proposal takes you too far, too soon. Simplicity is your ally right now — don't trade it away until a real customer or scale problem forces the change.
